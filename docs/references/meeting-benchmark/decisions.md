## #7 화자 수정 범위 3단계

- **결정**: `recording:reassignSegment`에 선택 인자 `scope`(`one` | `forward` | `all`)를 더한다. 인자가 없으면 `one`이다. 범위 계산과 병합은 `src/main/services/speaker-correction.ts`에 있다.
  - `one`: 그 세그먼트만 바꾼다.
  - `forward`: 같은 회의에서 그 세그먼트의 현재 화자(화자 없음 포함)와 같은 화자를 가진 세그먼트 중, 정렬 순서(start_ms, sort_order, id)로 그 세그먼트와 같거나 뒤에 있는 것을 모두 바꾼다.
  - `all`: 그 화자의 세그먼트를 모두 바꾼다. 원래 화자와 대상 화자가 둘 다 있으면 `recording:mergeSpeakers`와 같은 병합(목소리 centroid 가중 평균, 원래 화자 행 삭제)을 한다.
  - 바뀐 세그먼트는 모두 `speaker_corrected = 1`이다. 빠른 재적용이 이 지정을 보존한다.
- **근거**: 세그먼트마다 `speaker_id`가 있고, 수동 교정 보존(`speaker_corrected`, `matchCorrectedSpeakers`)과 병합 경로(`mergeSpeakerVoices`)가 이미 있다. 범위 계산만 더하면 된다. "전체"를 병합과 다른 경로로 만들면 목소리·표본 처리 규칙이 두 벌이 된다.
- **한계**: `one`·`forward`는 화자 centroid를 다시 계산하지 않는다. 오디오 없이 계산할 수 없기 때문이다. 섞인 클러스터의 centroid는 섞인 채로 남는다. 정확한 centroid가 필요하면 참석 인원을 지정해 다시 나눈다.
- **보류**: 되돌리기(undo), 구간을 드래그해 고르는 범위 선택.

## #8 녹음 종료 시 참석 인원 확인

- **결정**:
  1. 녹음 화면에서 종료를 누를 때 참석 인원 입력이 비어 있으면 "참석 인원은 몇 명이었나요?"를 묻는다. 수를 고르면 `recording:setExpectedSpeakers`로 저장한 뒤 종료·처리한다. "모르겠어요 · 자동"을 고르면 지금처럼 자동 추정이다. 창 닫기·앱 종료 가드가 부르는 저장 경로는 묻지 않는다.
  2. `meetings.speakers_confirmed`(0/1) 열을 둔다. 자동 추정으로 처리된 회의(`expected_speakers IS NULL`, `speakers_confirmed = 0`)를 열면 상세 화면 머리에 "화자를 자동으로 N명으로 나눴습니다. 실제 참석 인원이 맞나요?"를 띄운다. [맞아요]는 N을 저장한다. 다른 수를 고르면 저장한 뒤 빠른 재적용(재전사 없음)으로 다시 나누고 요약도 다시 만든다. 닫기도 확인으로 친다.
  3. `recording:setExpectedSpeakers`는 항상 `speakers_confirmed = 1`을 함께 쓴다. 녹음 시작 때 인원을 지정했으면 처음부터 1이다. 마이그레이션은 기존 회의를 모두 1로 둔다(옛 회의 45건에 배너가 뜨지 않게).
- **근거**: CLOVA Note는 녹음 직후 인원을 묻는다. 처리 전에 물으면 화자분리를 한 번만 돌린다. 하지만 사용자가 그 순간 답하지 않거나(자동 선택) 가드 경로로 저장되는 경우가 있으므로, 처리 결과를 보여 주며 한 번 더 묻는 경로가 필요하다. 재분리 경로(`setExpectedSpeakers` + `recording:process` `skipTranscribe`)는 이미 있다.
- **보류**: 화자별 발화 시간이 짧은 클러스터를 근거로 "N명보다 적어 보입니다" 같은 추정 문구.

## #9 발화 점유율

- **결정**: 화자별 발화 시간(세그먼트 길이 합), 비율(최대 나머지 방식으로 합 100%), 발언 횟수(연속 같은 화자 묶음 수)를 계산하는 순수 함수를 둔다. 렌더러와 main(Markdown)이 같은 규칙과 같은 테스트 표를 쓴다.
  - 타임라인 탭의 "화자 비율"을 "발화 점유율"로 바꾸고 이름·시간·비율·발언 횟수를 보인다.
  - 회의록 Markdown에는 화자가 2명 이상일 때 `## 발화 점유율` 섹션을 전사 앞에 넣는다.
  - 화자 없는 세그먼트는 "미지정" 줄로 맨 뒤에 둔다.
- **근거**: 타임라인에 이미 비율 막대(`speakerTotals`)가 있다. 계산을 순수 함수로 빼면 Markdown과 화면 수치가 어긋나지 않는다. 무음 컷편집 뒤에는 컷 구간 대부분이 지워지므로 컷 구간을 따로 빼지 않는다(화면과 Markdown 모두).
- **보류**: 끼어들기 횟수, 화자별 말 빠르기, 시간대별 점유율 그래프.

## #10·#11 회의 유형별 템플릿, 녹음 중 메모·북마크

- **결정**: 템플릿은 지시문만 바꾼다. 출력 스키마(tldr·keywords·topics·decisions·action_items·open_questions)는 바꾸지 않는다. 기본 4종은 코드 상수다(`src/main/services/meeting-templates.ts`). 회의별 고정은 `meetings.summary_template`(NULL=자동), 실제로 쓴 템플릿은 `meeting_summaries.template_id`에 둔다. 자동 선택은 사용자 제목 정규식이 맞으면 그 형식이고, 아니면 같은 요약 호출에서 모델이 내용으로 고른다(F3).
- **메모**: `meeting_marks` 테이블(`src/main/services/meeting-marks.ts`). `raw_ms`는 녹음 경과 시각(불변), `at_ms`는 현재 오디오 시간축 시각이다. 컷편집 때 `at_ms = mapMsToCompacted(raw_ms, keep)`로 다시 계산한다(`origin='live'`만). 북마크는 text가 빈 메모다. 요약 프롬프트에 `[사용자 메모]` 블록을 넣고, 각 메모 시각 앞 90초~뒤 10초 전사는 샘플링에서 빠지지 않게 고정한다. 주제 카드 배정은 렌더러가 시각 구간으로 결정론적으로 한다.
- **근거**:
  - `meeting-summary.ts`의 출력 키 블록은 이미 갈아끼울 수 있게 분리돼 있다.
  - `meeting_summaries.meeting_id`가 UNIQUE이고 할 일 연결(todo_id)이 action_items JSON 안에 있다. 그래서 스키마를 넓히는 안은 소비처(SummaryPanel, 시각 재매핑, Markdown, 비서)를 모두 고쳐야 한다.
  - LLM이 출처를 표시하게 하면 표시가 틀릴 때 "사용자 줄은 신뢰"라는 구분이 무너진다.
  - 재매핑 함수(`remapExistingTimelines`)는 구역마다 실패를 무시한다. 불변 `raw_ms`에서 다시 계산하면 복구 비용이 낮다.
  - `foreign_keys`가 켜져 있어(`src/main/db/database.ts`) 초안 회의를 지우면 메모도 함께 지워진다.
- **추가 결정**: 같은 문장의 액션아이템은 재요약 뒤에도 할 일 연결(todo_id)을 이어받는다(공백·문장부호를 뺀 소문자 비교). 템플릿을 바꿔 다시 요약할 때는 확인창을 띄운다.
- **파일 소유 조정**: 출력 키 블록 상수와 템플릿 모듈은 데이터·IPC 담당이 만들고, 요약 서비스는 그것을 가져다 쓴다. IPC(`recording:setSummaryTemplate`)가 템플릿 id 검증을 써야 하는데, 요약 서비스와 서로 기다리는 순환을 피하기 위해서다.
- **보류**: 사용자 정의 템플릿 편집기, 캘린더·이력 기반 자동 선택(녹음과 일정을 잇는 경로가 없다), custom_sections, LLM 출처 표시(note_ids), 전역 단축키, 타임라인 북마크 마커, 한 회의에 요약 여러 개, 메모 단어를 whisper 힌트로 쓰기.

## #12 과거 회의 소급 매칭(Rematch)

- **결정**: 등록된 구성원 프로필로 옛 회의의 화자를 다시 매칭한다. 매칭 규칙은 `src/main/services/voiceprint.ts`의 `planVoiceMatches`를 그대로 쓴다.
  - 대상: 상태가 transcribed·summarized인 회의의 화자 중 목소리 centroid가 있고, 이름이 비어 있고, 연결이 없거나 제안(suggested)인 화자.
  - 후보 좁히기: 그 회의의 참석자. 그 회의에서 이미 다른 화자에 연결된 구성원은 뺀다. 화자별 거부 목록(`rejected_member_ids`)도 지킨다.
  - 목소리 모델 id별로 프로필을 따로 계산한다(모델이 다르면 비교하지 않는다).
  - 2단계로 동작한다. 미리 보기(바뀔 화자 목록)를 보여 준 뒤, 사용자가 적용을 누르면 같은 계획을 트랜잭션으로 다시 계산해 쓴다. 자동(auto)은 이름까지 붙이고, 제안(suggested)은 연결만 한다.
  - 특정 구성원으로 좁혀 실행해도 2순위 점수 차는 모든 구성원으로 계산한다. 그래야 좁혔다고 자동 지정이 늘지 않는다.
  - 진입점은 두 곳이다. 인식 보조 > 구성원(전체·구성원별 "지난 회의에서 찾기")과 화자 탭("등록된 목소리로 다시 찾기", 그 회의만)이다.
- **근거**: 매칭 계획 함수는 이미 순수 함수다. 프로필은 사용자가 이름을 지정·확정할 때만 생긴다. Rematch는 표본을 만들지 않으므로 동의 없는 프로필 수집이 늘지 않는다.
- **알아 둘 것**: 지금 실데이터는 구성원 표본 0건, 화자 목소리 3건이다. 당장 효과는 작고, 목소리 등록이 쌓이면 효과가 커진다. Rematch로 붙인 이름은 이미 만든 요약에는 반영되지 않는다. 요약을 다시 만들면 반영된다.
- **보류**: 등록 직후 자동 Rematch, 이름이 붙은 화자를 덮어쓰는 재매칭.

## #13 회의 간 AI 질의

- **결정**: AI 대화의 in-process MCP 서버(`src/main/services/ai-tools.ts`)에 읽기 전용 도구 `search_meetings`·`get_meeting_excerpt`를 더한다. 도구 정의는 `src/main/services/ai-meeting-tools.ts`에 둔다. 검색은 LIKE 다중 키워드(OR)이고 점수로 정렬한다. 도구 결과에 `linkwork://recording/{id}/at/{ms}` 링크를 미리 넣어 주고, 렌더러는 그 링크로 녹음 상세를 열어 그 시각부터 재생한다. 상한은 검색 8,000자, 원문 12,000자·10분 창, 질의당 누적 60,000자다. 질의에서 회의 도구를 한 번이라도 쓰면, 사용자 메시지에 있는 호스트라도 `fetch_url`은 승인 카드로 보낸다.
- **근거**: 회의 45건, 전사 약 67.5만 자라 LIKE 전체 스캔으로 충분하다. FTS5 trigram은 3자 미만 질의를 못 받는데 한국어 핵심어는 대부분 2음절이다. 파생 색인은 갱신 지점이 다섯 곳 이상이라 어긋날 위험이 있다. 감사, 읽기 전용 커넥션, 자동 허용 목록, 링크 처리는 이미 있다.
- **보류**: 회의록 화면의 "회의에 질문" 진입점, `ai_chats.scope` 서버 강제, 인용 레지스트리·칩 UI, 추천 질문, FTS5 색인(회의가 수백 건을 넘거나 검색 실측이 50ms를 넘을 때), 로컬 임베딩, 문서 화면 시각 링크.

## #15 화자 평가 세트 + 모델 교체 검토 — 평가 경로만

- **결정**: 앱 기본 모델·임계값·model-manager는 바꾸지 않는다. 다음 평가 경로만 만든다.
  - `src/main/services/diarization/cli.ts`: `--emit-segments 1`
  - `scripts/diar-regress.mjs`: `--model`, `--dump-hyp`
  - `scripts/eval/eval_diar.py`: `--hyp`
  - `scripts/eval/diar_bench.py`(라벨 없는 지표 + oracle/auto DER)
  - `scripts/eval/label.py`: `--prefill`, `--minutes`

  후보 3종(CAM++ 현행, ERes2NetV2, WeSpeaker ResNet34_LM)은 라벨 없는 1차 비교만 실제로 돌린다.
- **1차 비교 결과**(회의 7건, `diar_bench.py --mode label-free` 기본 `--chunk 200` 산출물 `out/diar_bench.md`): 모든 모델이 크래시 없이 끝났다. CAM++는 통과했다(1on1 5/5가 2명, 53↔50 margin 0.334, 회의 51 40.5초·최대 창 2.24초, 총 131.7초). ERes2NetV2도 라벨 없는 기준은 통과했다(1on1 5/5가 2명, margin 0.237로 CAM++보다 좁음, 회의 51 162.1초로 180초 한도 근처, 회의당 약 4배 느림, 총 549.8초). CAM++ 대비 라벨 불일치는 1on1에서 1.4~2.0%, 회의 51(3명 대 4명)에서 12.2%, 회의 44(1명 대 2명)에서 19.1%다. WeSpeaker ResNet34_LM은 7건 모두 1명으로 나눠 탈락했다(1on1 0/5, 불일치 19.1~47.0%). ERes2NetV2는 라벨 DER 판정 대상으로 남는다.
- **크래시 원인과 조치**: 처음 비교에서 ERes2NetV2(회의 50·51·44·45)와 WeSpeaker(51·44)가 SIGTRAP으로 죽은 원인은 메모리 부족이다. sherpa-onnx-node 1.13.3은 창(스트림)마다 받은 네이티브 메모리를 돌려주지 않는다. 고정 길이 창에서도, GC를 강제해도, 이벤트 루프에 양보해도, 추출기를 다시 만들어도 회수되지 않았다. 그래서 RSS가 창 수에 비례해 는다(ERes2NetV2 약 8MB/창, 회의 50에서 7.6GB까지 오른 뒤 죽음. CAM++ 약 3MB/창). 평가 경로는 cli `--chunk N`이 창 임베딩을 N개씩 자식 프로세스에 맡기고 클러스터링은 부모가 한다. 임베딩 값은 나누지 않을 때와 같다(회의 53 CAM++ 가설·목소리 일치 확인). `diar-regress.mjs --chunk`와 `diar_bench.py --chunk`(기본 200)가 이 옵션을 넘긴다. 앱 경로도 같은 방식으로 창 300개마다 워커를 나눈다(F1). ERes2NetV2로 바꾸게 되면 청크 크기만 줄이면 된다.
- **근거**:
  - `scripts/eval/refs/`에는 템플릿만 있다. cli 출력에는 세그먼트별 화자가 없다.
  - DB의 화자 가설은 지금 알고리즘의 결과가 아니다(53·51은 1명, 50은 7명). 그래서 라벨 미리 채우기는 현행 cli 출력으로 해야 한다.
  - 구성원 표본이 0건이라 교체 비용은 지금 가장 싸다. 그래도 라벨 DER 없이 교체할 근거는 없다.
  - Node로 DER을 다시 구현해 `check:diar`에 넣는 것은 refs가 gitignore 대상이라 이 Mac에서만 돈다. 비용에 비해 이득이 작다.
- **교체 판정 기준(다음 작업)**: 4개 회의의 가중 평균 oracle DER이 절대 3%p 이상 좋아져야 한다. 어느 회의도 2%p 넘게 나빠지지 않아야 한다. auto DER이 나빠지지 않아야 한다. 1on1 5건이 모두 2명으로 나뉘어야 한다. 회의 51 처리 시간은 180초 이하, 크래시는 0건이어야 한다.

## F1~F4 결정

#7~#15를 구현한 뒤 정한 후속 결정이다. 항목마다 결정·근거·한계·보류를 둔다.

### F1 화자분리 메모리 상한

- **결정**: 앱 경로를 "창 300개(`DIAR_CHUNK_WINDOWS`)마다 새 utilityProcess embed 워커 → 마지막에 cluster 워커 1개" 순서로 돌린다. 워커는 한 번에 하나만 산다(직렬). 조정 함수는 electron 을 import 하지 않는 `src/main/services/diarization/chunk-runner.ts`의 `runChunkedDiarization`(fork 주입)이고, `SherpaAdapter`가 `utilityProcess.fork`를 넘긴다.
  - main은 WAV 전체를 디코드하지 않는다. 헤더만 읽어(`readWavInfo`) 창을 계획한다. 디코드하면 61분 녹음 기준 main에 약 235MB가 일시적으로 잡힌다.
  - embed 워커는 자기 창이 덮는 샘플 범위만 읽는다(`readWavPcm16Range`). 워커당 오디오 메모리가 녹음 길이와 무관하다.
  - 클러스터링은 main이 아니라 cluster 워커에서 한다. sherpa 를 로드하지 않으므로 메모리가 작다(거리 행렬 64MB 이하와 임베딩).
  - 임베딩 함수·창 계획·`diarizeFromEmbeddings`는 그대로 쓰고, 숫자는 `number[]`로 보낸다(Float32 → double → Float32 왕복은 정확하다).
  - 전체 기한 30분, 취소(현재 워커 kill + AbortError), 워커 비정상 종료나 응답 수 불일치(reject → 단일 화자 폴백 note)를 유지한다. 진행률은 임베딩 0~0.95, 클러스터 0.95~1이다.
- **근거**:
  - sherpa-onnx-node 1.13.3은 창마다 네이티브 메모리를 돌려주지 않고(GC·양보·추출기 재생성 무효), 프로세스가 끝나야 회수된다. 단일 워커는 최대 메모리가 창 수에 비례해 2시간 회의에서 메모리 부족 위험이 있었다.
  - 설계 때 CAM++ 약 3MB/창으로 어림해 300창 ≈ 0.9GB + 워커 기본 약 0.2GB, 워커 최대 약 1.1GB로 잡았다.
  - 4,000창 AHC는 동기 CPU 작업이라 main에서 돌리면 창이 몇 초씩 멈춘다.
  - 메모리 부족은 같은 입력에서 결정론적으로 다시 나므로 재시도하지 않는다.
- **실측**(회의 51, 3,726창, 청크 300 → embed 워커 13개): 워커 하나의 최대 RSS는 약 1.2~1.25GB다. 창당 네이티브 메모리는 (5,489MB − 약 200MB) / 3,726 ≈ 1.4MB로, 설계 때의 3MB 어림보다 작다. 상한 판정은 `npm run check:diar-mem`(`scripts/diar-mem.mjs`, 빌드 엔트리 `diarization-mem-probe`로 앱과 같은 경로를 띄우고 250ms마다 프로세스 트리 RSS 합을 잼)으로 "트리 최대 RSS 2,048MB 이하"다. 결과 동일성은 `--compare-cli`로 회의 53을 단일 프로세스 cli 결과와 대조한다(세그먼트 화자 배열 완전 일치, 임베딩 최대 절대 차 1e-6 이하).
- **한계**: 워커마다 기동·모델 로드가 약 1초 더해진다(회의 51은 약 13초). `check:diar`(180초 한도)는 cli 경로라 영향이 없다. 실측은 이 Mac의 실제 녹음으로만 돈다.
- **보류**: 청크 크기 설정 UI, 병렬 워커(목적이 메모리 상한이라 직렬), ERes2NetV2 교체(이 구조에서는 청크 크기만 줄이면 된다).

### F3 템플릿 자동 선택

- **결정**: 녹음 시작 화면의 요약 형식 칩을 없앤다. 형식은 요약할 때 세 단계로 정하고, Claude 호출은 그대로 1회다(`resolveTemplatePlan`).
  1. `meetings.summary_template`이 유효하면 수동 고정이다(source `manual`).
  2. 아니면 사용자가 입력한 제목(`title_auto=0`)이 형식 정규식에 맞을 때 그 형식이다(source `title`, 이유 `제목의 "1on1"` 같은 일치 문자열).
  3. 둘 다 아니면 같은 요약 호출에서 모델이 고른다(source `auto`). 프롬프트에 `[회의 형식 고르기]` 블록(4개 형식의 선택 기준과 형식별 지시)을 넣고, 출력 JSON 맨 앞에 `template_id`(허용 목록)와 `template_reason`(50자 이하 한 문장)을 쓰게 한 뒤 고른 형식의 지시를 따르게 한다. 허용 목록 밖 id는 `default`로 바꾸고 이유는 NULL로 둔다.
  - 저장은 `meeting_summaries.template_id`(실제로 쓴 형식)·`template_source`·`template_reason`이다. 출력 스키마(tldr·keywords·topics·decisions·action_items·open_questions)는 그대로이고 메타 키만 더했다.
  - 요약 화면은 "형식: 스탠드업 · 자동"과 "자동 선택 이유: …"를 보인다. "형식 바꿔 다시 요약"에서 형식을 고르면 `summary_template`에 저장해 수동 고정하고, "자동(내용으로 판단)"을 고르면 NULL로 돌린다.
- **근거**:
  - 결정론 규칙만 쓰면 새 녹음이 모두 기본 제목(녹음 시작 화면에 제목 입력이 없다)으로 시작하므로 늘 default다. 새 녹음에서는 사실상 동작하지 않는다.
  - 모델만 쓰면 사용자가 "1on1"·"스크럼"처럼 분명히 붙인 제목이 무시될 수 있고, 결과가 실행마다 흔들린다.
  - 정규식이 맞는 경우는 정밀하고 비용이 0이다. 실DB 정규식 적중은 47건 중 15건(1on1 5건, 스크럼 6건, 리뷰 4건)이다. 맞지 않는 경우만 모델이 내용으로 판단한다.
  - 추가 비용은 프롬프트 약 900자(전사 한도 80,000자의 약 1%)와 출력 약 60토큰이고, 호출 수는 그대로다.
  - 별도 분류 호출은 지연과 사용량이 두 배라서 택하지 않는다.
- **한계**: 자동 선택의 정확도는 라벨로 재지 않았다. 형식을 잘못 고르면 사용자가 요약 화면에서 고정해 다시 요약한다.
- **보류**: 형식 선택 정확도 라벨 평가, 사용자 정의 형식.

### F4 요약 기반 자동 제목

- **결정**: 새 컬럼 `meetings.title_auto INTEGER NOT NULL DEFAULT 0`을 둔다. 1이면 시스템이 붙인 제목(기본 제목 또는 요약 제목)이라 요약이 덮어써도 되고, 0이면 사용자 제목이라 절대 덮지 않는다.
  - `recording:createDraft`는 제목 입력이 비면 '제목 없는 회의'와 `title_auto=1`, 입력이 있으면 0이다. `recording:rename`은 언제나 0이다. 마이그레이션은 컬럼을 붙일 때 기본 제목·빈 제목 행만 1로 둔다.
  - 같은 요약 호출의 새 출력 키 `title`(30자 이하 명사구)을 `normalizeSummaryTitle`로 정리한다(첫 줄, 제목 전체를 감싼 따옴표·괄호 쌍과 끝 마침표 제거, 공백 1칸, 30코드포인트, 비었거나 기본 제목이면 무시).
  - `applyAutoTitle`이 `UPDATE meetings SET title=? … WHERE id=? AND title_auto=1`로 바꾼다. title_auto는 1로 남아 다시 요약하면 다시 갱신한다.
- **근거**:
  - 요약 제목에는 패턴이 없어서 "다시 요약 시 자동 제목이면 갱신"을 제목 문자열 패턴으로는 판정할 수 없다. 그래서 플래그를 둔다.
  - 조건부 UPDATE라서 요약 도중 사용자가 이름을 바꿔도(rename이 먼저 0으로 바꿈) 덮지 않는다.
  - whisper 초기 프롬프트, 형식 정규식(F3), 자동 모드의 "회의 제목(사용자 입력, 참고용)" 줄에는 자동 제목을 쓰지 않는다. AI가 만든 문구가 다음 전사를 유도하거나(환각) 다음 형식 판단을 스스로 강화하는 것을 막는다.
- **한계**: 실DB 47건은 모두 사용자가 이름을 바꾼 제목(title_auto=0)이라 바로 바뀌는 행은 없다. 효과는 새 녹음부터 난다. 비서의 지난 회의 매칭은 제목이 같아야 하므로 자동 제목끼리는 잘 맞지 않는다(기본 제목도 원래 매칭에 쓸모가 없었으므로 악화는 없다).
- **보류**: 녹음 시작 화면의 제목 입력, 제목 후보 여러 개 중 고르기.

## 사람이 할 일

1. 구현 착수 전: 작업 트리에 남은 다른 팀의 미커밋 변경(`src/main/db/schema.ts`, `docs/MEETING_RECORDING.md`)을 커밋하거나 머지해 기준점을 만든다.
2. 배포(`npm run deploy`) 뒤 키체인 비밀번호 팝업이 뜨면 허용한다.
3. 실제 회의 2~3건(1:1·스탠드업·리뷰)을 녹음하고, 요약 화면의 자동 선택 형식·이유가 맞는지, 다뤄지지 않은 주제를 지어내지 않는지 본다. 제목을 비운 녹음은 요약 뒤 제목이 내용에 맞게 바뀌는지 본다.
4. 녹음 중 메모 3개 이상을 남긴 회의로 요약을 돌려 메모가 반영됐는지, 주제 카드 배정이 맞는지 본다. 60분 이상 녹음에서 북마크 시각과 재생 위치의 차이가 수 초 이내인지 본다.
5. 섞인 화자가 있는 회의에서 "이 구간부터"로 교정하고 빠른 재적용 뒤에도 교정이 남는지 본다.
6. 자동 추정으로 처리된 새 회의에서 참석 인원 확인 배너가 뜨는지, 다른 수로 다시 나누면 화자 수가 그 수가 되는지 본다.
7. 구성원 목소리를 등록한 뒤 "지난 회의에서 찾기" 미리 보기가 맞는 사람을 고르는지 본다.
8. AI 대화에서 회의 질문 3~5개를 해 보고, 출처 링크가 그 시각부터 재생되는지 본다. 평가용 질문 10~30개와 정답(회의·대략 시각)을 적어 둔다.
9. 평가 경로가 생기면 `scripts/eval/label.py`로 정답 화자를 라벨한다. 회의 53은 전체, 50과 44는 앞 10분, 51은 중간 10분을 라벨한다. 현행 가설로 미리 채운다(`--prefill`). 라벨이 끝나면 DER 판정을 요청하고, 기준을 넘으면 모델 교체(재등록 안내·재동의 포함)를 승인한다.
10. 후보 모델을 GitHub sherpa-onnx 릴리스에서 내려받을 때 권한 프롬프트가 뜨면 허용한다. 오디오는 외부로 나가지 않는다.
11. (#14 재검토 때) 안정 서명 인증서를 준비할지 정한다. 원격 회의는 소스를 mic+system으로 녹음하고 참석 인원을 지정한다.
